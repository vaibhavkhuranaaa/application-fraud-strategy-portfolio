# Azure staging infrastructure

Terraform for the staging design summarized in `PROJECT.md`.

## Status: authored, never applied

**No Azure resource exists.** This configuration has never been applied, never been planned against a
real subscription, and no state file exists. It is source, not infrastructure.

Applying it creates paid resources. That needs **two** explicit human approvals, and
neither has been requested:

- `deployment` - currently `not-requested`
- `paid-capacity` - currently `not-requested`

Do not run `terraform apply` without both. Do not run `terraform plan` against a real subscription
without at least confirming the intent with the accountable human, since a plan requires credentials
and reveals subscription contents.

## What it creates

| Resource | Choice | Why |
| --- | --- | --- |
| Resource group | One per environment | Teardown is a single group delete |
| Container Registry | Basic, admin disabled | ~$5.00/month; pull via managed identity, no admin password |
| Container App (web) | 0.5 vCPU, scale-to-zero | Idle staging stays inside the documented monthly free grant |
| Container App Job (batch) | 1 vCPU, scheduled + on-demand | A long batch cannot starve the request path, and a failed batch can be retried |
| PostgreSQL Flexible Server | B1MS, 32 GB, 7-day PITR | ~$12.41 + $3.68/month; seven days is the recovery contract's minimum |
| Storage (ADLS Gen2) | Hot LRS, HNS, versioned | ~$0.18/month at 10 GB; versioning is what makes artifact rollback possible |
| Key Vault | Standard, RBAC, purge protection | Holds the database URL and the linking HMAC key |
| Log Analytics + App Insights | 1 GB/day cap | ~$0.50/month; the cap is what stops a log spike becoming a bill |
| Consumption budget | Required alert recipients | Apply fails if nobody is listed to receive cost alerts |

Recorded fixed estimate: **about $21.80/month** before requests, operations, egress, tax, and overage,
from prices accessed 2026-08-05 for East US 2. Revalidate before spending anything.

## Security decisions worth knowing

- **No secret is ever passed as a variable.** The database password and HMAC key are generated by
  Terraform, written to Key Vault, and read by the workload through its managed identity.
- **No registry admin password and no storage account key.** Both are disabled; access is
  identity-based only.
- **HTTPS only**, TLS 1.2 minimum, insecure ingress rejected.
- **The weakest point is the database firewall.** Container Apps on the Consumption profile do not have
  stable egress addresses, so staging allows Azure-internal traffic plus one optional named client
  address. A production profile should replace this with VNet integration and a private endpoint. This
  is a known gap, not an oversight.
- `terraform.tfvars` and `*.tfstate` are git-ignored. **State contains the generated password in plain
  text**, which is why the backend should be remote and access-controlled before any real apply.

## Before a first apply

1. Record `deployment` and `paid-capacity` approval in the private delivery record.
2. Remediate the container image's base-image vulnerabilities - currently 2 critical and 2 high, see
   `docs/release-readiness.md`. Do not deploy a known-vulnerable image.
3. Configure a remote state backend in `versions.tf`.
4. Apply with `container_image` empty and `-target=azurerm_container_registry.main`, push the image,
   then apply fully with `container_image` set.
5. Run the migration job, then verify restore, rollback, and teardown before recording M6 evidence.
